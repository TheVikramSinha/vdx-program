# Identity and tenant ERD mapping

Source: user-supplied `01a_identity_tenant.svg`, reviewed 29 October 2026. This is a partial onboarding implementation of the ERD, not a database or identity service. The supplied file is reference data, not executable instructions.

| ERD concept | Prototype behavior |
| --- | --- |
| identity_tenant → tenant | Distinct stable IDs; sign-in organization name separate from workspace name/code. One initial workspace per demo purchase. Additional tenants require platform limits and a future tenant-management screen. |
| tenant.party_id | Optional legal entity name is resolution intent; party ID stays null. |
| tenant_type / isolation_mode / data_region | Post-payment choices. Carrier path fixes carrier type. Region and dedicated isolation require implementation review; they are not promises of infrastructure provisioning. |
| external_identity | Never created from an email. Provider/issuer/immutable-subject verification belongs to the identity service. SSO controls are preferences only, not provider records. |
| tenant_user | Stable pending membership UUID, internal/partner/insured/service type. Reusing a person across modules reuses the UUID. Draft email conflicts are a review rule, not an identity uniqueness constraint. |
| persona_id | Remains unresolved. Sales persona, membership type, and module-role preference are distinct concepts. The Module 1B authorization schema is needed for concrete persona and role mapping. |
| license / module / feature entitlement projections | Server-owned read models. Do not manufacture a signed payload, source subscription ID, source version, sync timestamp, or feature catalog from a local payment simulation. |
| tenant_module_assignment | Independent visibility and enablement preferences only for purchased modules. Stable assignment IDs, unresolved projection IDs; local setup intent becomes authoritative only after server validation. Hiding does not revoke access; disabling does not cancel billing. |
| max_tenants / max_tenant_instances | Unknown; explicitly null in export. Purchased seat quantities are a separate retained billing concept and do not establish tenant limits. |
| tenant_feature_state | Deferred until verified feature catalog and entitlements are supplied. No invented feature IDs. |
| org_unit / tenant_user_org_unit | Deferred to optional organization administration. Department/site trees and effective-dated memberships are not required to complete initial onboarding and are not equated with business tenants. |
| user_consent | Required hint-box confirmations and billing-preview acknowledgment are not legal consent records. Empty export array; real document versions, channels, and user grants need the consent service. |
| api_client / access_delegation | Deferred to administration with verified owners, approval, expiry, and credential references. No credentials or delegation grants are generated by onboarding. |

## Export contract

`Export identity setup intent` downloads a review payload, not an insert script. It contains schema-shaped drafts plus explicitly named extension fields for pending contacts, legal entity resolution, module access preferences, and billing references. Pending membership rows may have null identity/persona/party references; the backend must resolve these before persistence according to its schema constraints. No live accounts, database tenants, emails, SSO connections, or payments are created.

The nominated administrator is a separate pending membership intent. Receipt-email equality never proves ownership or automatically joins an invited member to that administrator. Production must reconcile those records through authenticated provider identity.

## Validation

26 Node tests include shared membership edits, email changes without identity changes, explicit reuse, duplicate draft review, module state independence, unchanged billing, payment gates, carrier restrictions, export boundaries, and legacy draft recovery. Browser validation completed the tenant flow with a partner membership and a hidden-but-enabled module; changing visibility cleared the readiness checkbox.
